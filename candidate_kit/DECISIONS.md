# DECISIONS.md

1. **Indexes.** I created a unique index on `emp_code` in `employees` and a unique compound index on `(emp_code, date)` in `attendance_logs` to guarantee data integrity and prevent race conditions. I added standard indexes on `employees.department` and `attendance_logs.date` and `status` to support the `$lookup` and `$match` stages in the analytics pipelines. I considered but rejected indexing the precise `punch_in` instant, as the analytics heavily filter by the calendar `date` string instead.
2. **Punch-in race.** When two identical punch-in requests arrive simultaneously, the app builds the document and calls `insert_one()`. The database's unique compound index on `(emp_code, date)` allows only one to succeed. The first gets a 201. The second triggers a PyMongo `DuplicateKeyError`, which the code catches in a `try/except` block and safely returns as a 409 Conflict.
3. **Ties.** The leaderboard pipeline uses `$setWindowFields` with `$rank` to calculate standard competition ranking. If multiple employees tie at the cutoff `limit`, they receive the same rank. Because the `$match` filter checks `rank <= limit` *after* ranking, all tied employees are returned (resulting in more rows than the limit). Tied rows are then ordered by `emp_code` ascending.
4. **Headcount.** The department summary pipeline starts by querying the `employees` collection (filtering by `joined_on`), not the logs. It then performs a `$lookup` (Left Outer Join) into `attendance_logs`. If an employee has zero logs, the lookup array is empty, but the employee document remains in the pipeline stream and still adds +1 to the final `$group` headcount sum.
5. **One thing you would change.** At 100x the data (~10 million records), running `$lookup` and `$densify` on the fly for every analytics request would be too slow. I would implement a materialized view or a daily pre-aggregated summary collection, updated asynchronously via MongoDB Change Streams or a background worker whenever a punch-out or regularization occurs.
